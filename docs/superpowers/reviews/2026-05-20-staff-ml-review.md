# Staff ML Engineer review of razorback v2

Date: 2026-05-20. Reviewer perspective: Staff ML Engineer. Repo state: main after PKG-13 ship (commit a2e9c49).

## TL;DR

The headline T14-honest result of "9/9 reward=1.0, Wilson 95% CI [0.7008, 1.0000]" is **statistically inflated**: the score reducer at `src/razorback/score/load.py:137-138` collapses three different bookreview questions (q1, q2, q3) into a single `"bookreview"` stratum, so 3 trials × 3 questions are reported as one binomial with n=9 even though q1/q2/q3 are different problems with different difficulties — this inflates effective N from 3 to 9 and tightens the CI from [0.4385, 1.0000] to [0.7008, 1.0000]. The PKG-13 substring-leak hardening (`bookreview_q1.py`, `bookreview_q2_q3.py`) **does not actually force live-DB queries** — the agent still has Read+Bash on the full `query_dataset/books_info.sql` dump (`prepare.py:202-210` whitelists `query_dataset/` verbatim into the workdir) and can compute correct short-form answers from the dump that fit under the 2000-char cap. The reachability gate (`prepare.py:266-276`) only proves postgres is **up**, not that the agent **used** it (PKG-13's own debriefing note H acknowledges this gap). Combined with three other shipped issues — `tools_denied` not enforced for the claude-cli path (the spec sets `temperature: 0.0` but it's also never threaded into the CLI argv), the `--against-constant` verdict for the stratified row carries no CI (point comparison only — a 0.578 vs paper-0.577 returns "above" identically to 0.95 vs 0.577), and Goal 1 plans to run on opus-4.7 while every existing data point and pre-registered shift band is on opus-4.5 — the upcoming Goal 1 numbers are at high risk of producing a second false-positive class of the same shape as T14. Recommend BLOCKER-level fixes before any $300-$500 burn.

## Findings (classified)

### BLOCKER (would invalidate the upcoming Goal 1 / Goal 2 numbers if shipped uncorrected)

- **[F1]** *Stratum-collapsing inflates effective N and tightens Wilson CIs across questions of heterogeneous difficulty.* Evidence: `src/razorback/score/load.py:137-138` (`_resolve_stratum` prefers `stratum.dataset` as the stratum label when present and scalar) and `packages/razorback-plugin-dab/src/razorback_plugin_dab/generate/stratum.py:10-17` (emits `{"dataset": "bookreview", "query_id": <int>, "backends": [...]}` per task). Because the loader picks `dataset` first, bookreview q1+q2+q3 all collapse into a single `"bookreview"` stratum. With trials=3 the reducer (`src/razorback/score/reduce.py:73-102`) sees n=9 binary outcomes and feeds Wilson with k=9, n=9 → [0.7008, 1.0000]. But the 9 outcomes are not 9 draws from one Bernoulli; they're 3 draws of q1, 3 of q2, 3 of q3 — three different problems. Why it matters: this is exactly the inflation pattern the captain asked about. At Goal 1 (N=5 × 3 variants × 12 datasets × avg 4.5 queries/dataset = ~810 trials) the stratum collapse will pool questions of wildly different difficulty into 12 strata, masking question-level variance and producing artificially narrow Wilson CIs vs the paper's 0.577. The paper's stratified pass@1 of 0.577 is defined as a mean over per-query pass-rates (or per-task; need to confirm), not as a single dataset-level binomial — so even a "matches" verdict here is comparing apples to a different kind of apples. Recommended fix: change `_resolve_stratum` to emit `f"{dataset}.q{query_id}"` (or otherwise stratify on the (dataset, query_id) tuple) so the Wilson CI is computed per-question (k=3,n=3 at smoke; k=5,n=5 at Goal 1), then the stratified mean (`src/razorback/score/reduce.py:49-53`) becomes a two-level macro: first within-dataset across queries, then across datasets. Alternatively keep `bookreview` as the rollup stratum but ALSO emit per-question rows and DON'T compute Wilson on the collapsed binomial — use a paired bootstrap or a per-question fixed-effects model. The bookreview "first honest 9/9" headline in `docs/superpowers/plans/2026-05-19-reconciliation-baseline.md:352-353` should be marked as "[0.4385, 1.0000] per-question (n=3) / [0.7008, 1.0000] is an over-pooled rollup."

- **[F2]** *Substring-leak hardening is bypassable — the agent still has Read+Bash on the full SQL dump in its workdir.* Evidence: `packages/razorback-plugin-dab/src/razorback_plugin_dab/generate/prepare.py:41-46` whitelists `query_dataset/` into the workdir; `prepare.py:202-210` copies the entire directory verbatim. `/Users/clkao/git/dataagentbench/data/query_bookreview/query_dataset/books_info.sql` is the full dump with `INSERT INTO books_info VALUES (...)` rows containing every title + year. Defaults at `src/razorback/agents/claude_invoke.py:7` are `("Bash", "Read", "Write", "Edit", "Glob", "Grep")`. The PKG-13 q1 hardening (`bookreview_q1.py:30-35`) only requires the answer text to PARSE as `^\d{4}s?$` matching ground-truth `"2020"`; an agent can `grep -oP "20[0-9]{2}" books_info.sql | sort | uniq -c | sort -rn | head` and find 2020 is the dominant year, emit `"2020"`, and pass without ever opening a postgres connection. The q2/q3 hardening (`bookreview_q2_q3.py:14`, `_ANSWER_MAX_LEN = 2000`) only blocks the dump-paste extreme; ground-truth book titles are literal substrings in the SQL dump (per the original PKG-13 cause description), so a `grep -E "^INSERT INTO books"` + extracting the title column + joining with commas yields a <2000-char answer that passes the upstream substring loop. Why it matters: the "honest" 9/9 PKG-13 number does not in fact prove live-DB queries happened — PKG-13's own side-finding H (reconciliation-baseline.md:431-438) admits "whether the agent actually queried postgres versus reading the SQL dump file is not directly observable." The reachability gate proves postgres is up; it does not prove the agent used it. If Goal 1 reproduces the same shape across 12 datasets, you will get a high number that says nothing about agent SQL competence. Recommended fix: either (a) remove `query_dataset/` from `_DATASET_SAFE` and rely solely on the live postgres/mongo + sqlite/duckdb file paths declared in `db_config.yaml` — i.e., the agent gets db_description.txt + db_config.yaml + query.json, NOT the raw SQL dump; or (b) audit the agent's bash transcript and add a Layer 3.5 detector that flags trials whose stdout shows a `cat */query_dataset/*.sql` or `grep .*query_dataset/.*sql` invocation. The simpler fix is (a); the SQL dump is supposed to be input for postgres at compose-up time, not a co-located cheat sheet for the agent. Stratum-by-stratum the same applies to mongo dumps (`prepare.py` does not selectively exclude them either).

- **[F3]** *`tools_denied` is configured but never enforced on the claude-cli agent path.* Evidence: `packages/razorback-plugin-dab/src/razorback_plugin_dab/generate/prepare.py:151` writes `settings.json` to `env_dir/settings.json` (i.e., `<task-dir>/environment/settings.json`); nothing mounts this into the container or symlinks it to `~/.claude/settings.json` where the claude CLI would actually read it. The claude-cli agent (`src/razorback/agents/claude_cli.py:113-117`) calls `build_claude_argv` which uses the 18-entry hardcoded `DISALLOWED_TOOLS` in `src/razorback/agents/claude_invoke.py:10-18` — NOT the 30-entry full upstream DAB list in `packages/razorback-plugin-dab/src/razorback_plugin_dab/generate/tools_denied.py:11-29`. Translate doesn't pass `tools_denied` for the claude-cli kind: `src/razorback/translate.py:204-207` only forwards `tools_allowed` and `sampling_temperature`. The two DISALLOWED lists disagree on 12 entries (the plugin's list includes uv pip / uv add / python -m pip variants the agent path doesn't block). Why it matters: Goal 1's AC-2 explicitly requires `tools_denied` populated with DAB's full DISALLOWED_TOOLS list in `provenance.yaml` (`docs/razorback-implementation/goal1-dab-paper-reproduction.md:57-61`). The provenance can be populated but it'll be a lie — the PreToolUse hook is structurally not wired. Recommended fix: either bind-mount `env_dir/settings.json` to `/root/.claude/settings.json` in the compose `main` service (the cleanest path, but requires `dab-agent:latest` to honor that path), or switch all DAB runs to the v2 agent (`SpacedockSolverV2`) which threads `tools_denied` to harbor's `ClaudeCode.disallowed_tools` per `src/razorback/agents/_runtime/claude.py:28-29`. The current state — having two DISALLOWED lists out of sync — is a maintenance hazard either way; consolidate to a single source of truth.

- **[F4]** *Spec-declared `temperature: 0.0` is unenforced on the claude-cli path.* Evidence: `src/razorback/agents/claude_cli.py:60` stores `self._sampling_temperature` but never references it again. `src/razorback/agents/claude_invoke.py:21-38` (`build_claude_argv`) does not emit any temperature flag in the `claude -p ...` argv. The PKG-13 T14 honest re-run and all reconciliation-baseline runs declare `temperature: 0.0` in the spec, but the claude CLI runs at whatever its default sampling is. Why it matters: every run-dir's reproducibility claim leans on "temperature 0.0" being enforced. If the claude CLI defaults to a non-zero temperature, Goal 1's "did we reproduce 0.577" question is mixed with a sampling variance the spec claims to have removed. The bookreview 9/9 may also partly reflect lucky non-zero-temperature sampling. Recommended fix: either thread a `--temperature 0` flag into `build_claude_argv` (verify the claude CLI accepts it; if not, add to the prompt or use `extra_args`), or DOCUMENT in the spec that `sampling.temperature` is **advisory** for the claude-cli kind. Right now the schema accepts a value the executor silently ignores — that's the worst combination.

- **[F5]** *`--against-constant` for the stratified row is a no-CI point comparison; "above" with mean=0.578 looks identical to "above" with mean=0.95 vs target 0.577.* Evidence: `src/razorback/score/verdict.py:70-77` (`_point_verdict`): only compares `mean > value` / `mean == value` / `mean < value`. `tests/unit/test_score_verdict.py:65-81` confirms this is the contract. Goal 1's primary reproduction claim is "spacedock variant pass@1 stratified mean vs paper 0.577" — but the verdict produces no uncertainty quantification at the aggregate level. The PER-STRATUM CIs go in, but the AGGREGATE pass@1 has no CI per `verdict.py:46-50` (`stratified.verdict` is "matches/above/below" with no `ci` field). Why it matters: Goal 1's headline reproduction claim will read "stratified pass@1 = X; paper's published = 0.577; verdict: above/below" — the captain will not know whether 0.55 or 0.60 is "reproduced." A 0.01-point gap from a noisy 60-trial measurement is not the same as a 0.01-point gap from a 1000-trial measurement. Recommended fix: ship a paired-bootstrap or normal-approximation CI on the stratified mean (the bootstrap kit at `src/razorback/diff/stats.py:87-123` is already there for `rk runs diff`; lift it into `against_constant`). At minimum, refuse to emit a "matches" verdict on the stratified row when each stratum's Wilson CI has a half-width > some threshold (i.e., admit when the data is too noisy to call it).

### IMPORTANT (would weaken the claim or its reproducibility)

- **[F6]** *Pre-registered 0.70-0.90 shift band is methodologically suspect; the post-hoc rationalization in the T14 re-run section walks it back.* Evidence: `docs/superpowers/plans/2026-05-19-reconciliation-baseline.md:386-399`: "The pre-registered expected-shift band ... for the harbor-DAB live-DB bookreview pass@1 was [0.70, 0.90]. Result: pass@1 = 1.000 with Wilson 95% CI [0.7008, 1.0000]. Point estimate exceeds the upper edge (0.90); the lower-CI bound just touches 0.70. With N=9 the CI is wide enough that the band is not strongly rejected — interpret as 'in-band or above.'" Why it matters: this is exactly the post-hoc rationalization the captain asked about. A pre-registered band that the point estimate exceeds and that gets "re-interpreted" as "in-band" via CI envelope is no longer a falsifiable prediction. Also, the pre-registered band [0.70, 0.90] is itself not in the pre-registration table at line 110-122 of the same doc — the table predicts direction ↓ and magnitude -0.10 to -0.30 vs the v1 dump-file score of 1.000, which implies a target band of [0.70, 0.90] OR [0.70, 0.90] for the LIVE-DB. The pre-reg is consistent with itself but the "re-interpretation" is loose. Recommended fix: at Goal 1 dispatch, pre-register the shift band per (variant, dataset) BEFORE the runs land, and write the methodology check as "outside the pre-reg band → mechanism failure or model strictly better/worse than predicted" without "CI envelope makes it close enough" softening. The reconciliation doc itself has the right discipline at line 124-130 (`AC-6 acceptance criterion`) — apply it strictly.

- **[F7]** *Goal 1 plans to use opus-4.7 but every existing data point + pre-registered shift band is on opus-4.5.* Evidence: `docs/razorback-implementation/goal1-dab-paper-reproduction.md:14-21` ("opus-4.7 + hints ON"); `docs/razorback-implementation/plans/goal1-dab-paper-reproduction.md:99-105` (T0 explicitly flags "the same auth path on opus-4.7 is unverified"); but the entire reconciliation-baseline doc records `claude-opus-4-5` results (`pkg13-bookreview-claude-harbor-dab-n3.yaml:7` confirms the PKG-13 spec model). Goal 1 will run a different model against pre-registered bands derived from opus-4.5. Why it matters: Anthropic models do not honor `seed` (spec ack at line 1102 of the spec doc); changing the model changes the sampling distribution, so the pre-reg bands' "expected magnitude" is calibrated to the wrong model. Recommended fix: either re-run the bookreview smoke at opus-4.7 to anchor the bands, or document in Goal 1's plan that the pre-reg bands are now **directional only** for opus-4.7 (no magnitude assertion). The current state — silently swapping the model — invalidates the pre-registration.

- **[F8]** *Three workspace-README variants are semantically distinct only at the surface level; an opus-class model can probably ignore the differences.* Evidence: `packages/razorback-plugin-dab/src/razorback_plugin_dab/generate/workspace_readme.py:10-84`. Variants:
  - `direct-minimal` (lines 10-20): 7 lines, no workspace layout block, no DB connection hints.
  - `direct-structured` (lines 22-51): adds a tree-view layout + explicit "Database access" block listing `host: dab-postgres, port 5432, user postgres, password postgres`.
  - `spacedock` (lines 53-84): same workspace layout + DB access as direct-structured, but reframes as "You are the first officer of the data-agent crew" and adds one sentence "Drive the analysis through the `model -> analyze -> verify` stages and commit a final answer that survives an honest verifier."
  Diff between direct-structured and spacedock is roughly 4 lines of prose framing. The DB connection details are IDENTICAL across direct-structured and spacedock. Why it matters: the paper's claim is that "spacedock" (a workflow-driven prompt strategy) outperforms a "direct baseline." If the only difference at the prompt level is 4 lines of framing prose (no separate scratchpad mechanism, no tool changes, no actual stage gates), then the spacedock variant is just direct-structured + a sentence. Goal 1 will measure 0.577-vs-0.4376 against a delta the prompt does not realize. The expected effect size of "first officer of the data-agent crew" framing on opus-4.7 SQL competence is, prior to data, small. Recommended fix: either (a) make the spacedock variant actually run through a multi-stage workflow (which is what the original DAB paper's spacedock prompt does), or (b) acknowledge in Goal 1's reproduction-doc methodology that "spacedock" here is shorthand for one prompt variant, NOT a faithful reproduction of the paper's workflow architecture. The current state is a reproduction in name only.

- **[F9]** *Stratified pass@1 is an unweighted macro-mean over datasets with wildly different query counts (2 to 13).* Evidence: `src/razorback/score/reduce.py:49-53`: `stratified_mean = sum(per_stratum_means) / len(per_stratum_means)`. `packages/razorback-plugin-dab/src/razorback_plugin_dab/datasets.py:17-28`: query counts are agnews=4, bookreview=3, crmarenapro=13, DEPS_DEV_V1=2, GITHUB_REPOS=4, googlelocal=4, music_brainz_20k=3, PANCANCER_ATLAS=3, PATENTS=3, stockindex=3, stockmarket=5, yelp=7 (total = 54 queries). Why it matters: the DAB paper's "stratified pass@1 = 0.577" — does the paper macro-average over datasets (each dataset weighted equally, regardless of 2 vs 13 queries) or micro-average over queries (each query weighted equally, regardless of which dataset)? The current implementation does macro-over-datasets. If the paper does micro-over-queries, 0.577 is being compared against a different statistic; the reproduction claim is misframed. ALSO: if the per-dataset stratum stays "bookreview" (collapsing 3 queries) the macro-average treats DEPS_DEV_V1 (2 queries) equally to crmarenapro (13 queries) — high-variance datasets (small q-count) get the same vote as low-variance ones. Recommended fix: read the DAB paper's exact stratification recipe and document which one razorback's `rk score` implements. If they disagree, add a `--strat-recipe` flag (`unweighted-macro` vs `query-weighted`). The plan at line 116-120 of `goal1-dab-paper-reproduction.md` is silent on this.

- **[F10]** *`docker_image_override` and per-task image pinning is partial.* Evidence: `src/razorback/spec/schema.py:151` (`docker_image_override: str | None = None` for ade-bench); `packages/razorback-plugin-dab/src/razorback_plugin_dab/generate/compose.py:14` (`DEFAULT_AGENT_IMAGE = "dab-agent:latest"`). The freeze pipeline (`src/razorback/provenance/freeze_cmd.py:55-57`) resolves the image digest if `spec.provenance.pin_image_digest=True` (default), but the resolved digest is written to `provenance.yaml`, NOT injected back into the docker-compose used at run time. So the agent container at run time is `dab-agent:latest` (mutable tag), while the digest in provenance is a snapshot from freeze time. If anyone rebuilds `dab-agent:latest` between freeze and run, the digest in provenance and the actual digest of the container don't match. Why it matters: Goal 1 plans to freeze 36 specs then dispatch them serially over hours of wall-clock; an image rebuild mid-burn would silently change the container. Recommended fix: at compose-generation time, substitute the agent image with the digest-pinned form (`dab-agent@sha256:...`) if `provenance.image_digest` is set in the frozen spec. Or document that "image digest in provenance is informational, not enforced." Either way, fix the silent gap.

### MINOR (methodology hygiene)

- **[F11]** *`Spec.trials: int = 1` default means N=1 runs produce Wilson CIs.* Evidence: `src/razorback/spec/schema.py:203` defaults trials to 1. At N=1 the Wilson CI per query is k∈{0,1}, n=1 → either [0.0, 0.7937] or [0.2063, 1.0]. Goal 2 explicitly rejected N=1 (`goal2-ade-bench-haiku-baseline.md:20-23`: "N=1 was rejected because Wilson CIs at N=1 are uninterpretable"), but the SCHEMA still accepts it without a warning. Recommended fix: emit a degeneracy marker in `rk score` output when any stratum has `n_completed < 3` (interpretable threshold; can be tuned). The marker should NOT prevent the run, only ensure the output is unambiguous about "this CI is not interpretable."

- **[F12]** *Verifier accepts `reward >= 1.0` as pass — but the SQL dump grep attack yields reward 1.0 with no robustness check.* Evidence: `src/razorback/score/load.py:94` (`passed=(reward is not None and reward >= 1.0)`). Combined with F2, this means even one accidental dump-grep success counts as a "pass." Recommended fix (long-term): grade on partial credit (e.g., 0.5 for partial answer, 1.0 for fully correct), and reserve "pass" for high-confidence cases. Short-term: keep the binary but document the brittleness.

- **[F13]** *No random seed pinning for the matrix dispatcher.* Evidence: `docs/razorback-implementation/plans/goal1-dab-paper-reproduction.md:236-263` (T2 dispatch loop) has no `--seed` flag. The spec schema has `sampling.seed: int | None = None` (`src/razorback/spec/schema.py:14`) but doesn't propagate it to the agent argv (claude doesn't honor seed anyway per `claude_cli.py:94`). Goal 1 will run 180 trials × ?-non-zero-temperature; whatever variance shows up is unattributable to seed vs sampling vs model drift. Recommended fix: capture model_version timestamp in each run-dir's `provenance.yaml` (resolvers.py:33-59 does this); accept seed-irreproducibility as an inherent property of Anthropic models AND document it on the reproduction-doc headline ("paper's published 0.577 vs our 0.X measured at model_version Y on date Z").

- **[F14]** *Loader's stratum resolution is fragile — falls through to "first scalar field" if `dataset` is missing.* Evidence: `src/razorback/score/load.py:140-143`. If anyone adds a new stratum field before `dataset` in the JSON, the loader silently picks up the wrong key. Recommended fix: make `dataset` mandatory (raise on missing); kill the "first scalar" fallback or move it behind a `--strat-key` CLI flag.

- **[F15]** *Verifier reward is read from `verifier_result.rewards.reward` or "first scalar" — same fallback fragility.* Evidence: `src/razorback/score/load.py:100-107`. Recommended fix: require `reward` key explicitly.

## Variant differentiation check

All three variants share the same output contract ("write to answers.json"), the same DB connection details (host `dab-postgres` port 5432, user/password `postgres/postgres`), and the same query-file location (`query.json`). The diffs:

| Variant | LOC | DB info | Layout block | Framing |
|---------|-----|---------|--------------|---------|
| direct-minimal | 8 | absent | absent | terse |
| direct-structured | 28 | explicit (postgres / mongo / sqlite / duckdb) | yes | task-oriented |
| spacedock | 30 | explicit (same as above) | yes | "first officer of data-agent crew" + "model -> analyze -> verify" sentence |

The spacedock variant adds **one paragraph** of role-framing prose vs direct-structured. There is no separate scratchpad, no enforced stage gating, no tool changes. An opus-4.7 model will likely treat all three as semantically equivalent for solving SQL problems; the expected pass@1 delta between direct-structured and spacedock, prior to data, is small (single-digit percentage points). The DAB paper's spacedock-vs-direct delta of 14 points (0.577 - 0.4376 = 0.1394) almost certainly comes from a richer workflow architecture than "one prose paragraph." Goal 1's reproduction claim should not be framed as "we reproduce 0.577 with the spacedock variant" without acknowledging that this spacedock IS NOT the paper's spacedock — it's the paper's prompt-prefix swap stripped of the workflow architecture. (Cross-ref: F8.)

## Verifier integrity

- **bookreview q1 (bounded-decade)**: `bookreview_q1.py:30-49`. Requires answer to parse as `^\d{4}s?$` and equal "2020". This BLOCKS the original PKG-13 false-positive (answer `"2020s"` accepting `"2020"`-substring match in essays). It does NOT block an agent that reads `books_info.sql`, counts year frequencies, and emits `"2020"`. The fix closes the dump-paste-verbatim path; it does not close the dump-read-and-compute path. Hardening is necessary but not sufficient.
- **bookreview q2/q3 (length cap)**: `bookreview_q2_q3.py:14`, `_ANSWER_MAX_LEN = 2000`. Blocks pasting the full SQL dump (which is ~70KB). Does NOT block an agent that greps titles from the dump and emits a comma-separated list. Ground-truth book titles are literal strings in the dump; the upstream substring loop accepts them regardless of source.
- **Other dataset verifiers**: `packages/razorback-plugin-dab/src/razorback_plugin_dab/verify/validators/__init__.py:1-3` is just a docstring; `_hardened_template` in `prepare.py:345-352` returns `None` for any dataset != bookreview. So agnews, crmarenapro, googlelocal, yelp, etc. fall back to the **upstream validator unchanged** (`prepare.py:337`). The upstream validators are also substring-based (per PKG-13's bug surface). Goal 1 will run against 11 datasets whose validators have ZERO leak-hardening. The PKG-13 work hardened only bookreview because that's where the false positive surfaced; the same class of bug is open on every other DAB dataset.

The verifier integrity gap is wider than PKG-13's bookreview-focused fix. Goal 1 should not dispatch until either: (a) each of the 12 datasets gets its own hardened template, OR (b) the workdir contamination root cause (F2) is fixed at the workdir-population layer so substring leaks become impossible regardless of validator shape.
